## 需求分析：Proposal 异步澄清回路（Web → RabbitMQ → Worker → 本机 WorkBuddy → MCP 回写 → 用户澄清 → Story）

**定性**：不是"加队列"，而是跨 3 个进程边界（AgentBoard 服务端有状态权威 / Worker 无状态 / WorkBuddy 一次性无记忆）的**有状态多轮人机协同状态机**。

**现状差距（探索结论，含行号）**：
- 无 Proposal 实体。当前 "proposal" = `Task.spec` Markdown 文本（`agentboard/domains/work_items/models.py:26`），MCP `spec_proposal`（`mcp_server.py:461`）只是拼 Markdown 写回该字段。本需求 Story 尚未诞生，proposal 无处可挂 → **必须新建独立表**。
- Notification 表 + API 已就绪（`identity/models.py:38-52`、`api.py:1411-1463`），前端铃铛为轮询（`app.ts:2834 loadNotifications`）。**无 WS/SSE**，但本需求轮询已够。
- **完全无 MQ/Celery/APScheduler**；调度靠自研 `DaemonScheduler` 线程轮询（`scheduler.py:226-247`）。
- MCP 97 个工具，统一走 `_http(method, path)`（`mcp_server.py:52`）。
- `service.generate_tasks_from_spec`（`service.py:438`）解析 `- [ ] 标题` 生成子任务，可复用于 P3 定稿转化。

**关键设计决策**：
1. **会话续接选"无状态重放"而非 `--resume`**：每轮把原始需求 + 全量 QA 历史重拼 prompt。幂等、可重试、可换机；代价是 token 线性增长（≤5 轮可控）。resume 会把 session 绑死在特定 Worker 目录，崩溃即废。
2. **WorkBuddy 提问后必须退出进程**，一轮 = 一次完整生命周期，产出「一批问题」或「一份定稿」。挂起等人类回答会耗尽 Worker 槽位且不可恢复。
3. **MCP 是单向出口**：只能 WorkBuddy → AgentBoard 写回，AgentBoard 无法反向唤醒。所以"用户答完继续分析"只能靠重新入队实现。
4. **MQ 只传 `{proposal_id, round}`，绝不传需求正文**；DB 是唯一事实源。`round` 作乐观锁，回写时 round 不匹配直接拒绝 → 防消息重投重复提问。
5. **身份归属坑**：`MCP_REQUIRE_AUTH=0` 时调用方 key 不生效，全部回写记在服务端 token 名下。解法=回写归属由 `proposal_id` 反查项目/提出人，Worker 用权限收敛的专用 abk_ 服务账号。
6. **RabbitMQ 可能是过度设计**：1~2 台 Worker 时用 `DaemonScheduler` + Worker 轮询 `/api/proposals/pending` 即可。MQ 价值在多 Worker 竞争消费、死信重试、办公网/公网解耦。
7. **不让 WorkBuddy 直接 create_story**：转化由服务端在用户最终确认后执行，保留人类闸门。

**状态机**：draft → queued → analyzing → awaiting → (用户答复 round+1 回 queued) → converged → converted。`analyzing` 超时（建议 30min）扫描回退 queued 防悬挂。

**建议表**：`proposal`(status/round/max_rounds/converged_spec/story_id)、`proposal_round`(round_no/worker_id/run_status)、`proposal_question`(round_no/seq/question/answer/skipped)。
**建议 MCP 工具**：`proposal_get` / `proposal_ask` / `proposal_finalize` / `proposal_fail`。

**主要风险**：消息重投幂等；Worker 崩溃致 analyzing 悬挂；无人答复长期堵塞；重放 token 成本；**提问质量（模型爱问文档里就有的问题，需强约束先检索已有 spec 且单轮 ≤5 条）**；Worker 拉起本机 WorkBuddy 的 RCE 安全边界（限定工作目录、Prompt 与数据分离）。

**分期**：P0 Proposal 表+状态机+前端问答工作台（手工触发，先跑通人机闭环，价值最高风险最低）→ P1 MCP 工具 + Worker + 无头 CLI（先 DB 轮询）→ P2 接 RabbitMQ + 超时回退/死信 → P3 定稿转 Story/Task。

**状态**：仅完成分析，未写代码、未创建 openspec change。
