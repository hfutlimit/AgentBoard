AgentBoard 自动派单时序图

从 Story.confirm 用户闸门到 Task.done 评审回流的完整链路。 三层派单（DB 轮询 / MQ 广播竞争 / MQ 定向）+ CAS 兜底，MQ 消息只做提示，DB 才是事实源。

架构范式
事件驱动 + 状态机 CAS claim
消息中间件
RabbitMQ · broadcast / direct queue
回退路径
MQ 不可用 → 自动降级 DB 轮询（P1）

端到端派单时序

串联六个阶段：用户确认 → 任务广播 → 开发者竞争认领 → Agent 推进 → 评审定向 → Story 收尾。

设计铁律 · Truth Source

MQ 消息 只带定位信息（entity_type + entity_id）， 消费者一律先 GET /api/.../{id} 回查真实状态再决策。 MQ 丢失/重复/状态过期都不会导致错误执行 —— DB 才是事实源。 MQ 不可用时 run_mq_forever 自动回退 P1 轮询，正确性不变。

三层派单机制

不是单一机制，而是 DB 轮询 + MQ 广播 + MQ 定向 三层并存，按业务域选用。

P1 · 默认

DB 轮询

poll_once() 周期扫三类工作项：proposal / ticket_request / confirmed story。 任何 Worker 实例启动时默认走这条。

触发：定时器
并发：CAS claim rowcount=1
兜底：MQ 不可用时降级
P2 · 广播

MQ 竞争消费

task.available 发到 broadcast queue，N 个 Worker 抢一条。 抢到后还要走 DB CAS claim 才算赢，消息只是 hint。

触发：story.confirmed 事件
并发：RabbitMQ 抢 + DB 二次校验
冲突：409 → ack 丢弃
P2 · 定向

MQ 定向投递

task.assigned / review.requested 走 direct exchange， 只投到指定 agent 的专属队列，其它 Worker 收不到。

触发：assign-reviewer 指派
并发：单 consumer 独占
兜底：无 agent 绑定退广播

护栏与失败兜底

每层都有可观察的失败信号，不会"卡死等天亮"。三连失败 / 五轮驳回 / 超时未决都转人工。

Story 连续 3 次失败 → blocked
每次失败 unclaim 回退 confirmed 重入池；累计 3 次置 blocked 转人工（_story_fail）
Task 连续 5 轮驳回 → blocked
评审 reject 后回退 in_progress；累计 5 轮仍未收敛置 blocked（review_task）
评审 30 分钟超时 → 重派 reviewer
scan_review_timeouts 周期扫，未达 5 轮上限则解绑旧 reviewer 重派（assign_task_reviewer）
超租约 processing 停滞 → 自动回收
reclaim_stale / reclaim_stale_ticket_requests 兜底崩溃进程，重置回 queued（maintenance_loop）
