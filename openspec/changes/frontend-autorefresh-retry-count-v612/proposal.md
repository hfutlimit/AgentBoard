# Proposal: 后台自动刷新失败重试退避计数显示 — Epic 84 v6.12

## 问题
v6.9 落地了后台自动轮询刷新（每 30s 静默 `loadRoute(false)`），v6.10 补齐了失败态的「自动刷新失败」低调提示条 + 一键重试，v6.11 又补齐了成功路径的「已同步」轻提示 + 恢复成功 toast。但失败提示条目前仅告知「自动刷新失败」与「重试」入口，**缺少可量化的重试进度**：用户无法知道后台已经重试了几次、下一次自动重试还要等多久。失败是持续过程（api.service 对 5xx 走 1+2+4s 指数退避重试，单次同步可能持续数秒到数十秒），没有计数与倒计时，用户只能被动等待且无从判断是否「卡死」，体验不对称。

## 目标
在 v6.10 失败提示条内补齐**可量化的重试进度反馈**，与 v6.10 失败条 / v6.11 成功轻提示形成完整闭环：
- **重试次数计数**：新增 `autoRefreshAttempts` 信号，每次自动同步（含手动「重试」触发）进入失败分支时自增，成功分支归零。
- **距下次自动重试倒计时**：复用既有 `autoRefreshCountdown`（每秒心跳递减、归零触发下一次 `autoRefreshTick`），在失败条内实时显示「M 秒后自动重试」，让用户明确感知后台正在按节奏持续重试。
- **文案升级**：失败条由「自动刷新失败 + 重试」升级为「自动同步失败（第 N 次）· M 秒后自动重试 + 重试」。
- 复用既有 `autoRefreshFailing` / `refreshing` / `autoRefresh` / `autoRefreshCountdown` 信号，零后端契约变更。

## 范围
- 纯前端，零后端契约变更。
- 不影响 v6.6 手动刷新、v6.7/v6.8 刷新 toast、v6.9 自动轮询、v6.10 失败提示与重试、v6.11 成功轻提示的既有行为。

## 非目标
- 不做退避曲线可视化（仅展示次数与倒计时，不改重试算法）。
- 不做每周期成功 toast（已由 v6.11 在「恢复」瞬间处理）。
- 不改动 api.service 的指数退避重试实现。
