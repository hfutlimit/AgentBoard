# Design — 发布产物一致性护栏（Epic 98 P0）

## 设计目标

一句话：**让「交付物 ≠ 源码」这件事无法悄悄发生。**

关键洞察是，这类事故之所以能长期存活，不是因为难修，而是因为**没有任何测试看过交付物**。
所有既有测试（含 Epic 97 那两层护栏）扫描的都是 `agentboard/mcp_server.py` 这个源码路径；
而部署时装到生产机上的是 `dist/agentboard-webapi.zip` 里的同名文件。二者从未被放在一起比过。

所以本次的设计重点不是「再写一个检查」，而是**把校验对象从源码换成交付物**。

## 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A. 把 dist/ 移出 Git | 加进 `.gitignore`，改由 CI 产出 | 根除陈旧问题 | 本项目没有 CI 产物流水线；运维当前依赖仓库内 zip 直接取包，改动面大、会中断现有交付方式 | 否决（本次） |
| B. 打包时顺手校验 | 只在 `main()` 里加自检 | 改动最小 | 只有「有人主动打包」时才生效——而事故的本质恰恰是没人打包 | 否决 |
| C. 独立 `--check` + pytest 护栏 | 校验与构建解耦，测试套件每次都跑 | 无需任何人记得；CI/pre-push 可挂；失败信息直接给出修复命令 | dist/ 仍在 Git 里，需要提交产物 | **采纳** |
| D. 仅比对哈希清单文件 | 打包时写 `MANIFEST.sha256`，校验时比对 | 快 | 清单本身也会陈旧，且手改产物+改清单即可绕过；等于把信任转移到另一个陈旧文件 | 否决 |

方案 C 之所以胜出：它把校验的触发权从「人的记性」转移到「测试套件」。
只要有人跑测试，产物陈旧就必然暴露。

## 架构

### 1. 清单驱动：build 与 check 同源

重构前，`build_webapi_pkg` / `build_mcp_pkg` / `build_web_pkg` 三个函数各自硬编码复制逻辑。
若校验端再照抄一份「应该有哪些文件」，两份定义必然随时间漂移——那时护栏会开始说谎。

重构后引入单一事实来源：

```
package_specs()  ->  {pkg_name: {"trees": [(源目录, 包内前缀)], "files": [(源文件, 包内前缀)]}}
        |
        +-- expected_manifest(spec) -> {包内相对路径: 源文件绝对路径}   # 「应该长什么样」
                |
                +-- build_pkg()   照着清单复制 + 压包
                +-- check_pkg()   照着清单比对目录与 zip
```

`build` 和 `check` 消费同一个 `expected_manifest()`。构建规则一旦变化，校验规则自动跟随。

### 2. 三重比对

```
源码树 ──(expected_manifest)──> 期望清单
                                   │
                    ┌──────────────┼──────────────┐
                    ▼              ▼              ▼
                 缺失文件       多余文件       内容不符
              (新模块没进包)  (删了还残留)  (源码改了没重打包)
                    
dist/<pkg>/ 目录 ──────(check_zip)──────> dist/<pkg>.zip
                   条目集合 + 逐字节内容必须一致
```

第三重（目录 ↔ zip）是本次事故里最隐蔽的一层：真正被部署的是 zip，
而人工核对时看的是目录。二者脱节时，肉眼检查会给出错误的安全感。

### 3. 两层测试：文本层 + 运行层

| 层 | 文件 | 回答的问题 | 强度 |
| --- | --- | --- | --- |
| 文本层 | `test_epic98_release_artifact_parity.py` | 产物的字节是否等于源码？ | 快（秒级），CI 常驻 |
| 运行层 | `test_epic98_release_artifact_e2e.py` | 产物解压出来**能不能跑**？ | 慢（分钟级），端到端 |

文本层能发现「文件不一样」，但回答不了「装上去到底行不行」。
运行层解压 zip 到临时目录，用 `PYTHONPATH=<解压目录>` 拉起服务，
**完全不碰仓库源码**，然后：

- 打真实的 `/api/proposals` 全链路（证明 Epic 96 的模块 + 迁移确实随包发布）；
- 用 `inspect(engine).get_table_names()` 确认三张提案表被建出来；
- 在子进程里 `from agentboard import mcp_server` 并真调曾经损坏的 5 个工具
  （证明 Epic 97 的修复确实进了产物，且是运行期证据而非文本证据）；
- Playwright 打开产物托管的前端，登录 → 渲染 → 断言控制台零报错。

### 4. 护栏的自证

护栏最危险的失效方式是「永远为真」——比对逻辑写错，于是什么都拦不住，还给人以安全感。
因此加入 `test_check_mode_detects_tampering`：把产物复制到临时沙箱，
故意做两种篡改，断言 `--check` 必须非零退出且指名道姓：

1. 把产物里的 `_http(` 改回 `_api(` —— 复刻 Epic 97 事故；
2. 删掉 `domains/proposals/models.py` —— 复刻 Epic 96 事故。

这两种篡改正是历史上真实发生过的两类事故形态。

## 关键实现决策

**为什么 pytest 强校验只覆盖两个 Python 包？**
`agentboard-web` 的内容取决于前端是否重新构建（`frontend/dist/...` 优先，回退 `agentboard/web/static`）。
若强制要求它与本地前端构建产物一致，那么任何人只要跑一次 `npm run build` 而没重新打包，
测试就会红——这会让护栏变成噪声源，最终被人加 skip 忽略掉。
Python 包的内容 100% 由源码决定，可以做无歧义的强校验；web 包交给 `--check` 全量模式报告。
**护栏宁可覆盖得窄一点，也不能训练团队去忽略它。**

**为什么用子进程加载产物内的 `mcp_server`？**
测试进程已经 `import` 了仓库源码的 `agentboard` 包。若在同进程里再插入解压目录到 `sys.path`，
拿到的仍是 `sys.modules` 里的旧对象——测的还是源码，产物验证形同虚设。
子进程 + `cwd=解压目录` + `PYTHONPATH=解压目录` 是唯一能保证「加载的确实是产物」的方式。

**AST 检查为什么改成纯静态取模块命名空间？**
Epic 97 的版本用 `set(vars(mcp_server))`——需要真正 import 模块。
对产物副本 import 会产生副作用（且有上面的 `sys.modules` 冲突）。
本模块改为 `_module_level_names(tree)` 纯静态扫描顶层定义，无需导入即可完成同等检查。

## 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 产物提交进 Git 导致 diff 噪声大 | 本次可接受；长期解法是方案 A（CI 产出），已在 proposal 记为后续项 |
| 运行层 E2E 较慢（拉起两个 uvicorn + Chromium） | 与文本层拆成两个文件，CI 可分别调度；文本层秒级，足以拦住绝大多数陈旧 |
| 未安装 playwright 的环境 | `pytest.importorskip` 优雅跳过，不阻塞后端流水线 |
| 18001 MCP 容器仍跑旧代码 | 明确列为非目标；本次不触碰端口，容器加载新代码留独立运维窗口 |
